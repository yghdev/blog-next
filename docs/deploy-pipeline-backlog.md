# 发布流水线优化待办

> 制定时间：2026-10-30
> 触发：接入 `dsh-ssh-ops` 插件后复盘现有发布流程时发现的问题
> 状态：**仅记录计划，尚未实施**。所有数字均为 2026-10-30 实测，不是估算。
> 相关文件：`.dsh/skills/deploy-blog/`、`scripts/package-standalone.mjs`、`scripts/verify-assets.mjs`

---

## 0. 先说结论

插件改善的是**控制面**（不用在 ssh config / 多台机器之间来回切），**不是发布流水线本身**。
现有流水线的七道防线（干净工作区、产物版本戳、tar 层级断言、哈希核对、原子切软链、
失败回滚、隔离冒烟）都是对的，不该推倒重来。

真正值得改的只有两类：**传输体积虚高** 与 **验证覆盖缺口**。
下文六项按"收益 ÷ 风险"排序，P0 可以直接做，P2 需要单独排期。

### 实测基线（2026-10-30 发布 `15200ef`）

| 指标 | 实测值 |
| --- | --- |
| `dist/` 体积 | 386 MB |
| `dist-upload.tar.gz` | 99 MB |
| 上传速度 | 20 MB / 17 s ≈ **1.18 MB/s** |

| `*.map` 占位 | 2818 个文件 / **95 MB** |
| `.d.ts` / `*.md` / `next/dist/docs` | 2 MB / 3 MB / 4.6 MB |

## P0-1 打包裁掉运行期不需要的文件

**问题**：`tar.gz` 里 95 MB 是 sourcemap，另有 7 MB 类型声明与文档。
standalone 运行期一个都不加载，但每次发布都要完整上传。

**证据**：`dist/node_modules` 363 MB，其中 `*.map` 2818 个 / 95 MB、
`*.d.ts` 1707 个 / 2 MB、`*.md` 587 个 / 3 MB、`next/dist/docs` 4.6 MB。

**改法**：`scripts/package-standalone.mjs` 末尾加 `pruneRuntimeNoise()`，
删除 `**/*.map`、`**/*.d.ts`、`**/*.md`、`node_modules/next/dist/docs`。
`release.sh` 与远端 `deploy.sh` 都不用改。

**已验证**：复制一份 `dist` 裁剪后 386 → 266 MB，tar.gz 99 → 72 MB（**-27%**）；
用它起真实服务，现成冒烟 **23/23 通过**，另测 9 个页面（首页 / 后台 / 概览 /
编辑器 / 说说 / 媒体 / 设置 / 前台说说 / 归档）全部 200、样式表正常、无控制台报错。

**验收**：裁剪后 `tar.gz` ≤ 75 MB；`smoke-remote.sh` 23 条全过；页面无白屏。

**风险**：极低。唯一代价是线上排查不能直接读 map —— 需要时从 git 重建即可。

## P0-2 打包前断言「产物不比源码旧」

**问题**：`release.sh` 第 72 行在 verify 分支里 `npm run build`，但第 77 行是
`[ -d .next/standalone ] || npm run build` —— **目录存在就完全不重建**。
而 `scripts/stamp-version.mjs` 取的是 `git rev-parse HEAD`，不是产物来源。

**后果**：`--skip-verify --deploy` 在"改了代码但没重新 build"时，会打出一个
`commit=新哈希、reproducible=true` 的包，里面跑的是旧代码。
此时 **healthz 通过、资产比对也通过**（本地 dist 旧、线上也旧，两边"一致"）——
正是 `SKILL.md` 要防的那类"看起来成功"。

**改法**：`package-standalone.mjs` 打包前取 `app/ components/ lib/ next.config.ts`
的最新 mtime，若晚于 `.next/BUILD_ID` 的 mtime 就拒绝打包并提示先 `npm run build`。

**验收**：故意改一个组件文件后直接跑 `npm run build:dist`，必须报错退出；
正常构建流程不受影响。

**风险**：极低。六行代码，只加一道拒绝。

## P1-1 资产比对纳入 JS chunk

**问题**：`scripts/verify-assets.mjs` 第 34 行只筛 `.css`，日志输出
「2 个 CSS chunk 全部逐字节匹配」。真正承载交互逻辑的 **25 个 JS chunk（2.6 MB）**
完全没验。若 JS 没部署成功而 CSS 成功，这个检查照样报绿。

**改法**：把 `.js` 纳入同一套哈希比对，复用现有 `sha()` 与逐文件循环；
首页与后台登录页的反向引用检查同样扩展到 `.js`。

**验收**：输出从 2 个文件变成 27 个；人为删掉一个线上 JS chunk 时报错。

**风险**：极低。

---

## P1-2 上线后的可用性巡检

**问题**：服务器上没有任何 healthz 定时任务（`/etc/cron.d`、systemd timer 均无）。
现在只有部署那一刻的探活。手机端 502、OOM 之后要等人发现。

**改法**：`/etc/cron.d/blog-health` 每 5 分钟 curl 一次 `/api/healthz`，
失败写 syslog 并走已有通知渠道；或接入现成外部监控（任选其一，不重复建设）。

**验收**：手动 `systemctl stop blog` 后 5 分钟内能收到告警。

**风险**：低。注意别写成"失败即重启"——OOM 循环重启会放大故障。

## P2-1 用 rsync `--link-dest` 做增量部署

**问题**：一次真实发布只有 732 KB 文件变化，却每次重传 99 MB。
`rsync` 两端都可用（本地 3.4.1 / 远端 3.2.7）。
实测 `rsync -n -a` 到线上当前 release：**只传 2 个文件 / 4.2 MB**，speedup 768×。

**改法**：`deploy.sh` 的"解包到新目录"改为
`rsync -a --link-dest=../<上一版> dist/ 新目录/` —— 硬链接复用未变文件，
只传差异。新旧 release 共享 inode，磁盘也不会翻倍。

**验收**：隔离副本上跑通完整部署 + 冒烟；回滚仍可用；两版共享 inode 数符合预期。

**风险**：**中**。这是改生产部署脚本，必须先在隔离副本验证，单独排期，不与其它项混发。

---

## P2-2 备份清理规则统一

**问题**：`blog-backup` 的 `KEEP=14` 只清理 `blog-*.tar.gz`，
同目录的 `pre-deploy-*.db`、`server.js.before-upgrade` 从未被清过。
规则不一致会在某天变成"以为保留 14 份、其实是 14+N"。

另：备份内容只有 `images/` + `blog.db`，**不含** `deploy.sh` / nginx 配置 / systemd unit。
这些在仓库 `deploy/` 里都有（已核对线上 `deploy.sh` 与 `scripts/deploy.sh` 完全一致），
所以不是必须项；但若在服务器上直接改过配置而忘了提交，就只剩服务器这一份。

**改法**：把历史遗留文件纳入同一保留策略（或明确移动到独立目录）；
可选：备份清单里附一份 `config/` 的当前副本。

**验收**：`/root/blog-backups` 文件数稳定在 14（或明确的两类各自上限）。

**风险**：低。

## 不建议做的

| 想法 | 为什么不做 |
| --- | --- |
| 用插件替代 `deploy.sh` 的原子切换 | 软链 + 探活 + 自动回滚是对的，插件只是入口，不该接管部署语义 |
| 跳过隔离冒烟换速度 | 成本只有约 40 秒，而它验的是"真实库 + 真实产物"才能暴露的问题 |
| 引入 Docker / CI 一键发布 | 单人博客，现有流水线已覆盖 7 次历史事故，再加一层编排只会多一个故障面 |
| 为 AI 开放生产 root 的免密自动连接 | 权限面已经够用；自动化收益不抵风险 |

## 建议落地顺序

| 顺序 | 项 | 风险 | 主要收益 |
| --- | --- | --- | --- |
| 1 | P0-1 裁剪产物 | 极低（已验证） | 每次省约 27 s 上传 + 每版省 120 MB 磁盘 |
| 2 | P0-2 产物新鲜度断言 | 极低 | 堵住唯一的假成功通道 |
| 3 | P1-1 JS 资产比对 | 极低 | 覆盖从 2 个文件扩到 27 个 |
| 4 | P1-2 健康巡检 | 低 | 首次拥有"上线后"防线 |
| 5 | P2-1 增量部署 | 中（需隔离验证） | 上传 99 MB → 4 MB |
| 6 | P2-2 备份清理 | 低 | 消除隐性堆积 |

P0 与 P1 可以合成一次提交，跑一遍完整发布验证；
P2-1 单独排期，先隔离副本，再上线。
