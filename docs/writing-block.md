# 个人博客前端整体 UI/UX 优化与重构

## 0. 项目背景与本次任务定位

这是一个已经具备完整基础功能的个人博客项目，目前后端及管理功能已经基本完成，接下来主要进行前台页面的 UI/UX 优化。

本次任务涉及以下五个页面：

1. 首页（文章列表）
2. 说说页面
3. 归档页面
4. 友链页面
5. 关于页面

目前网站已经形成了一套比较明确的视觉风格，但不同页面之间还存在一些细节不统一、空间利用不合理、部分页面缺乏设计特色等问题。

本次不是重新开发博客，也不是更换主题，而是一次有明确边界的前端专项改版。

### 核心目标

在保留现有博客整体设计语言的前提下，提高页面的完成度、视觉辨识度和实际使用体验。

希望最终呈现出一个：

- 有个人特色，而不是模板化的博客。
- 简洁、克制，但不显得单调。
- 有设计感，但不为了设计而牺牲阅读体验。
- 不同页面各有特点，但又属于同一个完整的网站。
- 桌面端和移动端都有良好体验的个人博客。

请优先进行实际项目代码修改，而不是只制作静态 HTML 演示。

# 一、必须遵守的开发原则

这是本次任务最重要的部分，请严格遵守。

## 1. 不要盲目重构现有项目

开始修改之前，必须先完整了解项目结构。

需要检查：

- 当前前端技术栈及版本。
- 页面路由和页面模板。
- 全局布局组件。
- 左侧导航组件。
- 右侧侧边栏组件。
- 文章列表组件。
- 说说列表组件。
- 归档数据处理逻辑。
- 友链数据来源和数据结构。
- 关于页面的数据来源。
- 全局 CSS 和主题变量。
- 暗色模式实现方式。
- 响应式布局实现方式。

根据实际代码确认每个页面的实现方式。

不要假设项目一定使用某个框架，也不要根据页面外观擅自修改技术架构。

## 2. 保护现有功能

本次重点是前端改版。

禁止：

- 修改无关的后端业务逻辑。
- 擅自修改 API 接口和数据结构。
- 删除现有功能。
- 更改文章、说说、友链等数据的存储方式。
- 破坏现有评论系统。
- 影响文章发布、编辑和管理功能。
- 删除原有页面路由。
- 为了实现视觉效果而引入不必要的大型依赖。

如果某项功能需要修改数据接口，先判断是否可以通过前端适配实现。

确实无法避免时，先说明原因和影响范围。

## 3. 保留现有设计语言

当前博客的视觉特点：

- 暖白色背景。
- 柔和的灰色边框。
- 淡紫色作为辅助强调色。
- 标题使用具有衬线感的字体。
- 正文使用清晰易读的无衬线字体。
- 卡片采用适度圆角。
- 以留白和排版建立视觉层级。
- 整体偏向 Minimal / Editorial / Personal 风格。

这些特点应当继续保留。

不要擅自改成：

- 常见的 SaaS 管理后台风格。
- 大面积渐变和玻璃拟态。
- 过度圆润的互联网产品风格。
- 复杂的装饰插画。
- 大量阴影和浮动动画。
- 过度依赖图片的瀑布流布局。

本次改版的目标是让现有风格更加成熟，而不是换一种完全不同的风格。

# 二、全局布局与设计规范

在优化单个页面之前，先检查全局布局。

## 2.1 整体布局

目前桌面端采用三栏布局：

左侧：个人信息和导航。

中间：页面主要内容。

右侧：辅助信息。

这是合理的基础结构，建议继续使用。

但不同页面可以根据内容类型调整主内容宽度，但是左侧边栏尽量保持统一，目前友链页面的左侧边栏相比其他页面靠右。

### 左侧导航

左侧导航是整个博客最重要的品牌识别区域之一。

当前展示内容：

- 个人头像
- flechazo
- 站点简介
- 文章
- 说说
- 归档
- 友链
- 关于
- 主题切换
- RSS
- 设置

要求：

1. 所有页面的左侧导航必须保持一致。
2. 不允许因为某个页面取消右侧边栏，就导致左侧导航的位置明显移动，保持全页面一致。
3. 统一头像尺寸、站点名称字号和简介样式。
4. 导航项目保持相同的高度、图标尺寸和间距。
5. 当前选中状态应当明确，但不要过于突出。
6. 保留目前轻量边框和橙色选中提示点的设计。
7. Hover 状态保持克制。
8. 移动端应当有合适的导航适配方案。

### 主内容区域

不同页面采用不同的内容宽度策略：

- 首页：适合三栏布局，主内容保持适中宽度。
- 说说：适当增加内容宽度，突出阅读体验。
- 归档：使用较宽松的时间线布局。
- 友链：取消右侧辅助栏后，主内容可以适当扩展。
- 关于：文章正文保持合理阅读宽度，右侧目录继续保留。

不要强制所有页面使用相同的主内容宽度。

### 右侧辅助区域

目前右侧区域包含：

- 文章目录（部分页面）
- 站点统计
- 博客聚合
- 标签云

建议继续保留这些功能。

优化重点：

1. 统一模块标题样式。
2. 统一模块之间的垂直间距。
3. 降低统计模块的视觉权重。
4. 优化标签云的排列密度。
5. 聚合站卡片不要过高。
6. 文章目录需要有清晰的当前章节状态。
7. 没有右侧内容的专题页面不需要强制显示右侧栏。

### 滚动行为

检查当前是否存在多个独立滚动容器。

尤其关注首页截图中右侧栏和整个页面同时出现滚动条的问题。

目标：

- 默认使用整个页面统一滚动。
- 右侧栏优先采用 position: sticky。
- 避免无必要的 overflow-y: auto。
- 如果确实需要独立滚动，必须有明确的交互理由。
- 不允许出现两个滚动区域互相争夺鼠标滚轮事件的情况。
- 检查浏览器缩放、窗口高度变化和触控板滚动。

# 三、全局视觉系统

建议在现有样式基础上，整理统一的设计规范。

不要为了统一而强行更换已有颜色。

## 3.1 配色

保留现有暖白色背景与淡紫色强调色。

重点检查以下颜色在不同页面中的一致性：

- 页面背景色
- 内容卡片背景色
- 主文字颜色
- 次级文字颜色
- 边框颜色
- 强调色
- Hover 背景
- 选中状态
- 标签背景色

如果项目已经存在 CSS Variables，请优先复用。

避免在每个页面中重复写入不同的颜色值。

可以在现有主题变量体系中补充缺失的语义变量。

## 3.2 字体规范

保留当前标题与正文的字体搭配。

建议建立统一层级：

- 页面主标题：较大字号，适当使用衬线字体。
- 区域标题：中等字号，适当加粗。
- 文章标题：清晰、易读。
- 正文：保持舒适的行高。
- 英文辅助文字：小字号、大字间距、适当使用大写。
- 日期和元信息：弱化显示。

不要在同一个页面中混用过多字体。

## 3.3 圆角与边框

当前卡片设计比较克制，建议继续保留。

统一：

- 卡片圆角。
- 输入框圆角。
- 按钮圆角。
- 边框颜色。
- 卡片内部间距。

不要所有元素都使用超大圆角。

## 3.4 动画

统一交互动画规范：

- Hover 过渡时间建议控制在 150～250ms。
- 卡片可以轻微上浮。
- 图标可以有轻量颜色变化。
- 按钮需要有明确的点击反馈。
- 页面滚动和锚点跳转保持自然。

禁止：

- 大幅度缩放。
- 弹簧式过度动画。
- 无意义的持续动画。
- 影响阅读的背景动态效果。

遵循 prefers-reduced-motion。

# 四、首页：文章列表页面

## 4.1 当前情况

当前首页主要由以下部分组成：

- 搜索框。
- 文章卡片列表。
- 右侧站点统计。
- 博客聚合。
- 标签云。

目前整体结构合理，不建议进行大规模重构。

主要问题：

1. 文章卡片稍微偏高。
2. 内容列表的信息密度可以进一步优化。
3. 搜索框下方缺少轻量的内容入口。
4. 右侧边栏视觉权重略高。
5. 首页缺少一些能够体现个人特色的内容引导。

## 4.2 文章卡片优化

保留现有卡片风格：

- 白色或主题卡片背景。
- 轻量边框。
- 适度圆角。
- 标题、摘要、元信息的排列方式。

重点优化以下内容：

### 卡片高度

目前卡片上下留白略多。

建议适当减少：

- 卡片上下 Padding。
- 标题与摘要之间的间距。
- 摘要与元信息之间的间距。
- 卡片之间的垂直间距。

整体压缩约 10%～15%，但不要让页面显得拥挤。

### 标题

- 标题应当是卡片中最突出的内容。
- 保持适中的字号和字重。
- 长标题需要正确换行。
- Hover 时可以轻微改变颜色。
- 不要使用过大的字体。

### 摘要

- 保留文章摘要。
- 限制摘要最大显示行数。
- 超出部分使用省略号。
- 不同长度的摘要不能破坏卡片整体布局。
- 摘要颜色略弱于标题。

### 元信息

统一显示：

- 发布时间
- 预计阅读时间
- 浏览量
- 文章标签

这些信息应当排列紧凑，避免出现过多装饰图标。

标签采用轻量 Badge 风格。

如果文章没有标签，不显示空白占位。

### 卡片交互

- 整个卡片是否可点击，按照现有交互逻辑决定。
- 标题和链接 Hover 时提供反馈。
- 不要让卡片中的其他功能按钮受到整卡点击事件干扰。

## 4.3 搜索框优化

保留现有搜索框。

检查：

- 输入框高度。
- 圆角。
- 搜索图标位置。
- Placeholder 颜色。
- Focus 状态。
- 移动端宽度。
- 搜索结果展示。

如果现有搜索功能支持实时搜索，保留其原有行为。

不要为了美化而破坏搜索功能。

## 4.4 增加轻量内容导航

可以在搜索框下方增加一条简洁的分类入口。

例如：

全部文章 / AI / 开发 / 随笔

要求：

- 只有实际存在的分类才能展示。
- 点击后使用现有分类路由或过滤逻辑。
- 当前分类需要有明确状态。
- 不要增加过大的导航卡片。
- 不要重复展示已经存在的导航功能。

如果现有分类体系不适合增加此区域，可以不实现，不要擅自创建分类。

## 4.5 右侧区域优化

站点统计：

- 保留目前的统计数据。
- 保留数字突出、标签弱化的设计。
- 适当减少卡片高度。
- 统一卡片尺寸。
- 优化最后一张卡片单独占一行时的排列。
- 不要让统计区域过于抢眼。

博客聚合：

- 保留现有聚合站。
- 卡片高度适当缩小。
- 名称和描述保持层次。
- 图标统一尺寸。

标签云：

- 保留现有标签和数量。
- 优化标签之间的间距。
- 不同数量的标签可以使用统一的视觉风格。
- 避免标签过度拥挤。
- 如果标签很多，使用合理的展示数量和现有跳转功能。

## 4.6 首页最终效果

希望首页整体更像一个精致的个人内容阅读空间。

重点仍然是文章，而不是统计数据和装饰元素。

不要添加占据大量首屏空间的巨大 Hero。

# 五、说说页面

## 5.1 设计定位

说说是一个轻量的个人动态记录页面。

它与文章不同，不需要复杂的卡片结构。

当前采用纯文本列表和分割线的方式是合理的。

建议继续保留这种简洁感。

## 5.2 页面顶部

可以在标题旁边加入英文辅助标题：

MOMENTS / DAILY NOTES

标题仍然使用目前的页面标题风格。

不需要增加大型介绍区域。

可以在标题下方加入一行简短说明：

「记录一些不一定值得写成文章，但值得留下的瞬间。」

## 5.3 说说列表

考虑优化成轻量时间线。

推荐结构：

左侧：

- 月份或日期。
- 简单的时间标记。

右侧：

- 说说正文。
- 发布时间。
- 可选的图片或附加内容。

视觉要求：

- 不使用大型卡片。
- 不使用明显的阴影。
- 保留内容之间的细分割线。
- 正文使用舒适的行高。
- 长文本自然换行。
- 图片如果存在，需要控制最大宽度和圆角。
- 不同类型的内容不能产生明显的布局跳动。

如果时间线设计会明显增加复杂度，可以保留当前列表，只优化日期和分割线。

## 5.4 时间显示

日期格式保持统一。

建议：
2026年10月29日

也可以采用日期拆分样式，但必须保证移动端显示正常。

## 5.5 交互

- 说说内容如果包含链接，保持正确跳转。
- 图片支持正常查看。
- 如果有评论或互动功能，保留现有行为。
- 如果后台已经支持发布说说，不需要重复增加前台发布功能。

# 六、友链页面

## 6.1 当前设计评价

友链页面已经经过一次独立改版。

当前已经具有：

- 独立 Hero。
- 中英文标题组合。
- 友链统计。
- FRIEND DIRECTORY 区域。
- 独立友链卡片。
- 交换友链说明。

当前设计方向正确。

本次只进行局部优化，不允许推翻重做。

## 6.2 Hero 区域

保留现有主标题：

「互联网的另一端，也有有趣的人。」

保留英文：

FRIENDS & CONNECTIONS

保留现有描述：

「这里收藏着一些有趣的个人博客。每一个链接，都是一次跨越屏幕的相遇。」

保留当前黑色与紫色的标题强调方式。

优化要求：

1. 控制 Hero 的垂直高度。
2. 标题字号在桌面端和移动端合理变化。
3. 描述不要占据过多宽度。
4. 顶部英文编号与主标题保持合理距离。
5. 不要增加大型背景插画。
6. 不要增加无意义的装饰元素。

## 6.3 统计区域

保留目前的统计样式：

- 友链数量。
- 聚合站数量。

要求：

- 数字继续作为视觉重点。
- 说明文字保持弱化。
- 横向排列。
- 与 Hero 和友链列表之间保持清晰分隔。
- 统计数据必须从真实数据动态计算，不能写死。

## 6.4 友链卡片

目前只有四个友链，建议桌面端暂时采用两列布局。

避免三列布局下第二行只剩一张卡片的问题。

推荐结构：

桌面端：

- 两列。
- 卡片高度尽量统一。
- 头像固定尺寸。
- 网站名称和描述排列清楚。
- 域名作为辅助信息。
- 右上角保留外链图标。

平板端：

- 根据容器宽度决定一列或两列。

手机端：

- 默认单列。
- 卡片宽度占满内容区域。
- 不出现横向滚动。

卡片要求：

1. 继续保留当前轻量边框。
2. 不增加明显阴影。
3. Hover 时边框颜色和背景轻微变化。
4. 卡片可以整体点击。
5. 外链安全属性按照现有项目规范设置。
6. 头像使用 object-fit: cover。
7. 头像加载失败时展示统一默认头像。
8. 图片加载前预留固定尺寸，避免 CLS。
9. 网站名称过长时合理截断或换行。
10. 网站描述最多展示合理行数，避免高度不一致。

友链数据必须继续由现有数据源驱动。

## 6.5 聚合站区域

目前统计区域显示有两个聚合站，但主列表中没有明显独立展示。

建议在友链列表下方增加：

02 / BLOG HUBS

展示现有聚合站：

- 开往
- 笔墨迹

采用比普通友链卡片更轻量的展示方式。

可以使用横向排列的小卡片。

不要将聚合站与普通个人友链混在同一个列表中。

数量必须动态获取。

## 6.6 交换友链区域

保留现有交换友链说明、本站信息和申请要求。

优化信息层级：

- 区域标题。
- 一句话介绍。
- 本站友链信息。
- 复制按钮。
- 申请规则。
- 申请入口。

本站信息需要从真实配置中获取，不允许硬编码虚假数据。

复制功能必须复制正确的友链配置。

复制成功后显示轻量提示。

申请入口平滑滚动到现有评论区或申请表单。

必须保证现有申请流程和评论功能正常。

# 七、关于页面

## 7.1 设计定位

当前关于页面主要是 Markdown 文章形式。

内容包含：

- 我在做什么。
- 本站。
- 联系。

内容结构基本合理，但缺少个人介绍的视觉特色。

建议在保留原有信息的基础上，进行一次轻量的个人介绍页改造。

不要设计成求职简历，也不要做成复杂的个人作品集。

## 7.2 页面顶部

建议使用以下结构：

你好，我是 flechazo。

一个喜欢折腾技术、探索新事物的学生。

可以使用：

- 当前真实头像。
- flechazo 名称。
- 一句个人介绍。
- 少量兴趣标签。

不需要添加虚构的职业头衔、工作经历或个人成就。

## 7.3 我在关注什么

将当前内容整理成几个简洁的方向：

AI & Artificial Intelligence
Development & Programming
Self-hosting
Open Source

这些是方向标签，不需要全部做成大卡片。

可以采用轻量标签或者两列小型信息布局。

## 7.4 我正在做的事情

保留当前真实内容：

- 折腾各种自托管服务。
- 使用 AI 结对开发一些小工具。
- 研究如何把复杂的东西讲清楚。

可以对文字进行适当润色，但不要改变原本含义。

## 7.5 关于这个博客

重点介绍：

- 为什么建立这个博客。
- 博客主要记录什么。
- 目前采用的技术架构。
- 对内容和长期维护的想法。

特别注意：

当前项目架构必须通过实际代码确认。

不要继续展示已经过时的技术架构介绍。

如果当前使用自研前端、Halo、Next.js 或其他技术，必须根据项目实际情况准确描述。

## 7.6 联系方式

保留现有真实联系方式。

可以采用：

- 邮箱。
- GitHub。
- 博客友链。
- 其他现有社交链接。

没有配置的联系方式不要擅自生成。

## 7.7 右侧目录

关于页面继续保留右侧文章目录。

目录应该：

- 正确获取页面标题。
- 支持点击跳转。
- 正确显示当前章节。
- 不遮挡正文。
- 桌面端采用合适的 sticky 定位。
- 移动端根据空间决定是否隐藏或折叠。

# 八、归档页面

## 8.1 必须优先修复的 Bug

目前归档页面出现多处：

NaN 月

这是明确的功能问题，必须优先解决。

请先检查实际归档数据和日期处理代码。

重点排查：

1. 日期字段是否存在 null 或 undefined。
2. 日期字段是否为空字符串。
3. 时间戳是否使用了错误的单位。
4. 是否把秒级时间戳误当成毫秒级。
5. 日期字符串是否不符合 JavaScript Date 的解析格式。
6. 时区转换是否产生了异常。
7. 月份是否从错误的对象中提取。
8. 分组过程中是否存在无效日期。
9. 数据格式是否在前后端之间不一致。

不要通过简单替换 NaN 文本的方式掩盖问题。

需要修复真正的日期解析和分组逻辑。

## 8.2 日期处理要求

建立统一的日期解析逻辑。

要求：

- 正确处理项目当前使用的日期格式。
- 正确处理时间戳。
- 明确区分秒级和毫秒级时间戳。
- 对无效日期进行安全处理。
- 不允许无效日期进入月份分组。
- 所有日期使用统一的时区策略。
- 不允许不同页面出现不同的日期显示结果。

如果存在无法解析的历史数据，不要擅自修改数据库。

应当安全跳过，并在开发调试阶段输出必要日志。

## 8.3 归档页面设计

当前采用年份与文章列表的结构，建议继续保留。

但需要优化信息层级。

推荐结构：

2026    25 篇

10 月
10/29  deepseek制作视频-第二篇
10/29  文本模型如何生成视频

9 月
09/08  COC War Tool：花名册重构与成员更新优化
09/03  博客迁移记录

要求：

1. 年份为一级标题。
2. 年份旁边展示文章数量。
3. 月份作为二级分组。
4. 文章标题为主要内容。
5. 日期作为辅助信息。
6. 文章列表之间不要使用过大的间距。
7. 不需要为每篇文章创建大型卡片。
8. 可以采用轻量时间线或分组列表。
9. 月份分组之间保持合理留白。
10. 文章标题 Hover 时有轻量反馈。

## 8.4 归档页面空间优化

目前截图中存在较多垂直空白。

建议：

- 缩小月份标题与文章列表之间的间距。
- 统一文章行高。
- 缩小不必要的分组间距。
- 保留清晰的年份分隔。
- 不要为了压缩空间而让内容过于拥挤。

# 九、响应式适配

本次必须同时检查桌面端、平板端和移动端。

## 9.1 桌面端

重点检查：

- 左侧导航宽度。
- 中间内容最大宽度。
- 右侧栏宽度。
- 三栏之间的间距。
- 页面是否出现横向滚动。
- 友链页面取消右侧栏后的布局。
- 窗口缩小时布局是否平滑变化。

## 9.2 平板端

当屏幕宽度不足以容纳三栏时：

- 优先隐藏或折叠右侧辅助栏。
- 保留主要内容区域。
- 左侧导航可以根据现有设计调整为更紧凑的形式。
- 不要出现内容被挤压的问题。

## 9.3 手机端

重点检查：

- 导航是否合理折叠。
- 文章卡片是否占满合适宽度。
- 友链是否变成单列。
- 关于页面是否存在过长的横向布局。
- 日期和元信息是否换行正常。
- 代码块是否可以横向滚动。
- 图片是否超出屏幕。
- 右侧目录是否合理隐藏或折叠。
- 页面滚动是否流畅。

不要只通过缩小桌面端元素实现移动端适配。

必要时采用不同的布局方式。

# 十、性能与可访问性

1. 图片应设置合理的尺寸。
2. 头像和封面图片支持懒加载。
3. 图片加载失败有默认展示。
4. 避免图片加载造成布局偏移。
5. 动画不应影响页面性能。
6. 减少不必要的重复渲染。
7. 不要引入没有必要的依赖。
8. 按钮和链接应具备正确的语义。
9. 图标按钮需要有可访问名称。
10. 文字和背景保持足够对比度。
11. 交互元素支持键盘焦点。
12. 尊重 prefers-reduced-motion。

# 十一、开发执行流程

本次改版必须按照阶段进行，不允许不分析代码就直接大规模修改。

## 第一阶段：项目分析

先阅读项目结构。

输出：

1. 当前技术栈。
2. 页面路由。
3. 全局布局组件。
4. 五个页面分别对应的文件。
5. 右侧栏实现方式。
6. 日期处理逻辑。
7. 友链数据来源。
8. 主题变量。
9. 当前存在的问题。
10. 预计修改的文件。

此阶段先分析，不要立即修改代码。

## 第二阶段：全局布局和基础规范

优先处理：

- 左侧导航统一。
- 主内容容器规范。
- 右侧栏滚动行为。
- 全局字体层级。
- 颜色和间距变量。
- 暗色主题。

要求避免影响已经正常工作的页面。

## 第三阶段：逐个页面改造

建议顺序：

1. 修复归档 NaN 月问题。
2. 优化首页。
3. 优化关于页面。
4. 优化友链页面。
5. 优化说说页面。

每完成一个页面都需要检查实际效果。

不要一次性修改所有页面后才开始测试。

## 第四阶段：测试

必须检查：

- 首页文章列表正常。
- 搜索正常。
- 分类跳转正常。
- 说说内容正常。
- 归档年份和月份正确。
- 所有文章链接正常。
- 友链数量正确。
- 友链跳转正常。
- 头像加载失败有兜底。
- 本站信息复制正常。
- 友链申请功能正常。
- 关于页面信息正确。
- 右侧目录正常。
- 暗色主题正常。
- 移动端没有横向溢出。
- 全站没有明显双滚动问题。
- 后台和原有接口不受影响。

如果项目有现成测试体系，优先使用现有测试体系。

## 第五阶段：最终交付

完成后提供：

1. 修改文件清单。
2. 每个页面具体修改内容。
3. 归档日期问题的根本原因。
4. 全局布局调整说明。
5. 响应式适配情况。
6. 暗色主题检查结果。
7. 功能回归测试结果。
8. 尚未解决的问题。

如果某项功能没有完成，必须明确说明，不允许声称已经完成。

# 十二、最终验收标准

本次改版必须满足以下标准：

### 视觉方面

- 保留原有博客品牌风格。
- 页面之间具有一致性。
- 不同页面有自己的布局特点。
- 不存在明显的视觉割裂。
- 没有过度装饰。

### 功能方面

- 原有功能全部保留。
- 归档日期正常。
- 友链数据正确。
- 评论和申请流程正常。
- 搜索和文章跳转正常。

### 体验方面

- 页面滚动自然。
- 内容层级清楚。
- 留白合理。
- 桌面端和移动端均可正常使用。
- 明暗主题均有良好表现。

请始终记住：

这次任务不是把博客改造成一个全新的商业产品，而是让它成为一个更成熟、更有个人特色、更适合长期维护的个人博客。

在设计上保持克制，在细节上追求精致，在功能上优先保证稳定性。
